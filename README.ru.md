# VPN Stack

> Для параноидального сисадмина, который не доверяет готовым бинарникам, считает совет «просто возьми коммерческий VPN» личным оскорблением и не уснёт, пока не прочитает каждую строку кода, не сгенерирует каждый ключ на собственном железе и не убедится, что каждый пакет идёт ровно туда, куда сказано. Здесь всё собирается из исходников. Никаких чёрных ящиков. Спите спокойно :smile:

Самохостинговый VPN-сервер, объединяющий **AmneziaWG** (обфусцированный WireGuard) и **Xray REALITY** (VLESS-прокси) с внутренним резолвером **dnscrypt-proxy** — всё оркестрируется через Docker Compose. Оба VPN-компонента включены по умолчанию; любой из них можно отключить на конкретном хосте (см. [Выбор компонентов](#выбор-компонентов)).

## Архитектура

```
┌──────────────────────────────────────────────────────┐
│                  Docker network: vpn                 │
│                   172.20.0.0/24                      │
│                                                      │
│  ┌────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │    DNS     │  │  AmneziaWG   │  │    Xray      │  │
│  │ 172.20.0.2 │  │ 172.20.0.3   │  │ 172.20.0.4   │  │
│  │  DNS :53   │  │ VPN :<rand>  │  │ REALITY :443 │  │
│  │ (internal) │  │   (public)   │  │   (public)   │  │
│  └────────────┘  └──────────────┘  └──────────────┘  │
└──────────────────────────────────────────────────────┘
```

| Сервис        | Роль                                                      | Открытый порт      | Отключается |
|---------------|----------------------------------------------------------|--------------------|-------------|
| **DNS**       | dnscrypt-proxy — шифрует и аутентифицирует DNS-запросы    | 53 (только Docker) | следует за AmneziaWG |
| **AmneziaWG** | Обфусцированный WireGuard VPN-сервер                      | случайный/udp      | `ENABLE_AMNEZIAWG=0` |
| **Xray**      | VLESS + REALITY прокси                                    | 443/tcp            | `ENABLE_XRAY=0` |

Все AmneziaWG-клиенты принудительно используют внутренний DNS-резолвер через iptables DNAT — их DNS-запросы никогда не покидают сервер бесконтрольно. Xray-клиенты резолвят через публичные серверы из `config.json` — поэтому `dns` разворачивается только вместе с AmneziaWG.

## Требования

- Ubuntu **24.04 или новее** (протестировано на **24.04** и **26.04**)
- Доступ root или sudo
- `git` (сборка резолвит релиз-теги компонентов через `git ls-remote`) — поставьте заранее, если его нет (`apt-get install -y git`)
- Docker Engine + плагин Docker Compose (см. ниже)
- Открытые в облачном фаерволе порты **443/tcp** и случайно назначенный **UDP-порт AWG** (AWS Security Group, правила GCP VPC и т. п.)
- **≈1.5 ГБ RAM или swap на время сборки.** Всё компилируется из исходников; сборка Xray-core (тянет gVisor) по пику требует заметно больше, чем есть на машине с 512 МБ. На маленьком инстансе добавьте swap **до** `deploy.sh`, например:
  ```bash
  fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
  echo '/swapfile none swap sw 0 0' >> /etc/fstab   # сохранить после перезагрузки
  ```
  Без достаточной памяти сборку убивает OOM (`docker-buildx` падает, образ `xray` не достраивается). В рантайме нужна лишь малая доля этого — swap нужен исключительно для компиляции из исходников.

### Установка Docker

Если Docker ещё не установлен, используйте вспомогательный скрипт:

```bash
sudo ./docker-install.sh
```

Скрипт устанавливает Docker Engine, плагин Compose и плагин buildx из штатных репозиториев Ubuntu (`docker.io`, `docker-compose-v2`, `docker-buildx` из компонента `universe`, включён по умолчанию) — **сторонний apt-репозиторий или GPG-ключ не добавляется**. Он пропускает уже установленные компоненты и завершается с ошибкой на версиях Ubuntu старше 24.04.

> Примечание: `docker.io` зависит от Ubuntu-шного `containerd` и поэтому конфликтует со стеком `docker-ce` / `containerd.io` из `download.docker.com`. На свежем хосте это чистая установка; если на хосте уже стоят upstream-пакеты Docker, их нужно удалить (и убрать `/etc/apt/sources.list.d/docker.list`) перед переходом.

> Для продакшн-развёртываний также рассмотрите:
> - Правила фаервола (UFW, iptables или облачный фаервол)
> - Хардненинг SSH (нестандартный порт, отключение парольной аутентификации)
> - fail2ban или аналогичную защиту от вторжений

## Быстрый старт

```bash
sudo ./deploy.sh
```

Этот скрипт:

1. Проверит, что Docker и Docker Compose установлены
2. Определит релиз каждого **включённого** стороннего компонента (см. [Версии компонентов](#версии-компонентов))
3. Соберёт образы из исходников с тегом-версией (`amneziawg:<ver>`, `xray:<ver>`, `dns:<ver>`); kernel-модуль компилируется под ядро хоста
4. Сгенерирует серверные ключи AmneziaWG, случайные параметры обфускации и случайный UDP-порт (49152–65535)
5. Сгенерирует `docker-compose.yml` из шаблона — только с включёнными сервисами
6. Сгенерирует ключи Xray REALITY X25519 и Short ID
7. Запустит все сервисы через `docker compose up -d` (контейнеры именуются `vpn-amneziawg`, `vpn-xray`, `vpn-dns`)

Шаги 3–6 пропускают то, что отключено — см. [Выбор компонентов](#выбор-компонентов). В конце скрипт печатает порты, которые нужно открыть в облачном фаерволе.

### Версии компонентов

Каждое развёртывание (и повторное) определяет релиз каждого стороннего
компонента и собирает из него. По умолчанию берётся **последний релиз
upstream**; конкретный закрепляется переменной окружения перед `deploy.sh`:

| Компонент | Переменная | Upstream | Образ |
|-----------|------------|----------|-------|
| Xray-core | `XRAY_RELEASE` | XTLS/Xray-core | `xray:<tag>` |
| AmneziaWG (kernel-модуль **и** tools) | `AMNEZIAWG_RELEASE` | amnezia-vpn | `amneziawg:<tag>` |
| dnscrypt-proxy | `DNSCRYPT_RELEASE` | DNSCrypt/dnscrypt-proxy | `dns:<tag>` |

```bash
# последние версии всего (по умолчанию)
sudo ./deploy.sh

# закрепить Xray, остальное — latest
sudo XRAY_RELEASE=v26.6.1 ./deploy.sh
```

- Резолвинг использует обычный `git ls-remote` — без GitHub-токена и без `jq`.
  Тег всегда закрепляется до commit-**SHA**, и исходники фетчатся по SHA — так
  сдвинутый тег не может незаметно изменить сборку. Текущая версия видна как тег
  образа (`docker images`), поэтому lock-файл не ведётся.
- `AMNEZIAWG_RELEASE` управляет и kernel-модулем (собирается на хосте), и
  userspace-tools (в образе). Образ `amneziawg` тегируется релизом **tools** —
  тем, что реально лежит в образе; если в репозитории tools нет такого тега,
  tools откатываются на свой latest (с предупреждением в логе). Kernel-модуль —
  отдельный хостовый артефакт, (пере)собирается только `rebuild-amneziawg.sh`
  или при первом деплое.
- **Geo-базы** Xray (`geoip.dat`, `geosite.dat`) всегда берутся последними и
  намеренно не закрепляются; обновляются при каждой пересборке образа Xray.

### Выбор компонентов

Оба VPN-компонента разворачиваются по умолчанию. Выставьте флаг в `0`, чтобы
получить однопротокольный хост — например, когда вы раздаёте только VLESS-ссылки
или когда в конкретной сети проходит только AmneziaWG:

```bash
sudo ENABLE_AMNEZIAWG=0 ./deploy.sh    # только Xray REALITY (DNS уходит вместе с AmneziaWG)
sudo ENABLE_XRAY=0 ./deploy.sh         # только AmneziaWG + DNS
```

| Флаг | По умолчанию | Значения |
|------|--------------|----------|
| `ENABLE_AMNEZIAWG` | `1` | `1/0`, `true/false`, `yes/no`, `on/off` (регистр не важен) |
| `ENABLE_XRAY` | `1` | то же |

Отключить **оба** нельзя — разворачивать будет нечего, скрипт завершится с
ошибкой; для полного сноса хоста есть `cleanup.sh`.

**`dns` следует за AmneziaWG** и собственного флага не имеет: на внутренний
резолвер через DNAT заворачиваются только AWG-клиенты, а Xray резолвит через
публичные серверы из своего `config.json`. Поэтому `ENABLE_AMNEZIAWG=0` убирает
и контейнер `dns` (вместе со ссылавшимся на него `depends_on`) — на Xray-only
хосте работает **один** контейнер, `vpn-xray`.

Отключённый компонент означает, что:

- его образ не собирается, ключи не генерируются, а сервис не попадает в
  `docker-compose.yml`;
- при повторном развёртывании его контейнер удаляется
  (`docker compose up -d --remove-orphans`);
- для AmneziaWG снимаются и хостовые артефакты — `amneziawg-module.service` и
  `/etc/modules-load.d/amneziawg.conf`, — так что при загрузке модуль больше не
  подгружается и не пересобирается (уже загруженный остаётся до перезагрузки);
- **ключи, живые конфиги и клиентские файлы не трогаются.** Включив компонент
  обратно (`sudo ./deploy.sh` с флагом `1`), вы получите те же самые пиры и
  клиентов. Чтобы стереть их, используйте `cleanup.sh`.

Сгенерированный `docker-compose.yml` — источник истины о том, что развёрнуто на
хосте: `add-client.sh` / `remove-client.sh` читают его и работают только с
развёрнутыми компонентами, поэтому `./add-client.sh alice` на Xray-only хосте
создаст только VLESS-профиль.

## Управление клиентами

**Добавить клиента** одновременно в AmneziaWG и Xray (или в тот единственный
компонент, который развёрнут на хосте — см. [Выбор компонентов](#выбор-компонентов)):

```bash
./add-client.sh <name>
```

- Имя клиента может содержать только буквы, цифры, дефисы (`-`) и подчёркивания (`_`).
- Для AmneziaWG: создаёт `clients/<name>_amneziawg.conf` (файл импорта) и `clients/<name>_amneziawg.png` (QR для мобильного приложения), печатает QR в терминал.
- Для Xray: создаёт `clients/<name>_xray.vless` (ссылка `vless://`) и `clients/<name>_xray.png` (QR для мобильного приложения), печатает ссылку + QR в терминале.
- В любом случае пользователю нужен один артефакт на протокол: **файл/ссылка** для импорта на десктопе, либо **QR PNG** для сканирования телефоном.
- AmneziaWG перечитывается на лету (`awg syncconf`, без рестарта, существующие сессии не рвутся); Xray перезапускается (обычно менее 2 секунд).

**Удалить клиента** из обоих сервисов:

```bash
./remove-client.sh <name>
```

Пир AmneziaWG удаляется на лету через `awg syncconf`; контейнер Xray перезапускается. Каждая половина выполняется независимо, поэтому сбой в одной всё равно отзывает другую.

> Скрипты отдельных сервисов (`amneziawg/add-client.sh`, `xray/add-client.sh` и т. д.) работают по отдельности, если нужен только один протокол.

## Операционные сценарии

Сборник рецептов для типовых операций жизненного цикла. Все команды выполняются из корня репозитория на соответствующем сервере.

### 1. Свежее развёртывание

```bash
sudo ./docker-install.sh   # один раз, если Docker отсутствует
sudo ./deploy.sh
```
Откройте в облачном фаерволе два порта, которые он печатает (443/tcp + случайный UDP-порт AWG). О требовании к swap на маленьких инстансах см. [Требования](#требования).

### 2. Обновление / повторное развёртывание существующего сервера

**Обновление — это просто повторный деплой, ничего удалять не нужно.** Подтяните новый код и снова запустите тот же скрипт:

```bash
git pull              # или скопируйте изменения на сервер через rsync
sudo ./deploy.sh
```

`deploy.sh` **идемпотентен** и неразрушающий. На уже развёрнутом хосте он:

- **сохраняет** серверные ключи (`server_private.key`, `reality_keys.txt`) и **всех клиентов** — генерация ключей пропускается, если они уже существуют;
- **заново определяет релиз и пересобирает** образы `amneziawg`, `xray`, `dns` (latest по умолчанию или ваши пины `*_RELEASE`), поэтому подхватывается более новый релиз upstream; версия отражается тегом образа;
- **перегенерирует** `docker-compose.yml` из шаблона, поэтому изменения capabilities, маунтов или портов вступают в силу — как и изменившийся `ENABLE_AMNEZIAWG` / `ENABLE_XRAY` (сценарий 8);
- **переприменяет** хостовое правило `INPUT` и `/etc/modules-load.d/amneziawg.conf`, если они отсутствуют.

Изменившиеся контейнеры пересоздаются (несколько секунд простоя); неизменившиеся остаются работать.

**Две вещи, которые обычный re-deploy _не_ делает** — обрабатывайте их явно, если обновление их затрагивает:

1. **Изменения шаблонов не переносятся в живые конфиги.** `awg0.conf` и `config.json` генерируются **один раз** (из `awg0.tmpl` / `config.json.tmpl`) и затем владеют вашими живыми ключами, клиентами, пирами и маршрутами — поэтому `deploy.sh` никогда их не перезаписывает. Если обновление меняет `awg0.tmpl` (например, новые правила фаервола), нужно мигрировать живой `awg0.conf` вручную: сделать бэкап, перенести новый блок `PostUp`/`PostDown`, сохранив свои ключи в `[Interface]` и блоки `[Peer]`, затем `docker compose up -d --force-recreate amneziawg`. (Для `config.json` это редко нужно — он хранит ваших клиентов/маршруты, а не политику.)
2. **Kernel-модуль не пересобирается.** `deploy.sh` пропускает сборку модуля, если он уже загружен, поэтому переход на более новый релиз модуля AmneziaWG (или обновление ядра) требует сценария 3 (`rebuild-amneziawg.sh`).

Чтобы намеренно начать с **новыми** серверными ключами, удалите `amneziawg/conf/server_private.key` / `xray/conf/reality_keys.txt` (и соответствующие живые конфиги) перед повторным деплоем — но учтите, что это инвалидирует всех существующих клиентов.

### 3. Пересборка kernel-модуля AmneziaWG

Нужна после **обновления ядра** хоста (`.ko` собирается под конкретную версию ядра) или для перехода на более новый релиз модуля AmneziaWG. Контейнер сначала нужно остановить — `rebuild-amneziawg.sh` отказывается работать, пока он запущен:

```bash
docker compose stop amneziawg
sudo ./rebuild-amneziawg.sh
docker compose start amneziawg
```
Скрипт пересобирает модуль из определённого релиза (`AMNEZIAWG_RELEASE` или latest) в одноразовом Ubuntu-контейнере под вашу версию ядра, проверяет `.ko` через `modinfo`, атомарно устанавливает его, грузит через `modprobe`, сохраняет автозагрузку в `/etc/modules-load.d/` и автоматически откатывается на бэкап с меткой времени (`/var/backups/amneziawg-kmod/<kver>/`, 3 последних), если `modprobe` не удаётся.

### 4. Развёртывание на дополнительных серверах

Каждый сервер независим — повторите сценарий 1 на каждом хосте. Типичная схема — один **входной (entry)** сервер, к которому подключаются клиенты, плюс один или несколько **выходных (exit)** серверов, используемых как upstream'ы (см. сценарий 5). Между хостами нечего разделять, кроме VLESS-ссылок uplink, которые вы генерируете в следующем сценарии.

### 5. Создать клиента, выходящего через другой сервер (Xray chaining)

Перенаправляет Xray-трафик конкретного пользователя со входного сервера на выходной, пока остальные пользователи выходят локально. **AmneziaWG не цепляется — см. ограничение ниже; AmneziaWG-профиль пользователя всегда выходит на входном сервере.**

```
                          ┌─▶ Internet            (остальные / AWG выходят здесь)
entry ─VLESS/REALITY──────┤
                          └─▶ exit server ─▶ Internet   (зацепленный Xray-юзер выходит здесь)
```

1. На **выходном** сервере зарегистрируйте входной сервер как обычного клиента и скопируйте напечатанную VLESS-ссылку:
   ```bash
   ./xray/add-client.sh entry-uplink
   cat clients/entry-uplink_xray.vless
   ```

2. На **входном** сервере создайте конечного клиента, зарегистрируйте выходной сервер как upstream и направьте клиента через него:
   ```bash
   ./add-client.sh alice                       # профили AWG + Xray для пользователя
   ./xray/add-upstream.sh germany '<vless_ссылка_из_шага_1>'
   ./xray/set-route.sh    alice germany
   ```
   - `<tag>` (здесь `germany`) — псевдоним выходного сервера. Не может быть `direct` или `blocked`.
   - `<user>` — имя существующего клиента (поле `email`, заданное `add-client.sh`).
   - **Заключайте VLESS-ссылку в одинарные кавычки** — в ней есть `&`/`?`, которые иначе разобьёт shell.

   Теперь `alice` выходит в интернет с IP выходного сервера по Xray; её AmneziaWG-профиль по-прежнему выходит на входном сервере.

### 6. Сменить точку выхода клиента (re-route)

Направьте существующего пользователя на другой upstream или обратно на локальный выход. Переконфигурировать клиента не нужно — меняется только входной сервер:

```bash
./xray/set-route.sh alice israel    # отправить alice через upstream 'israel'
./xray/set-route.sh alice direct    # вернуть alice на локальный выход (входной сервер)
```
`set-route` — единственный источник истины для per-user правила пользователя: переключение заменяет старое правило, а `direct` удаляет его полностью. Пользователи без правила используют локальный outbound `freedom`. Контейнер Xray перезапускается при каждой операции (обычно менее 2 секунд).

> **Chaining для AmneziaWG не реализован.** `add-upstream`/`set-route` управляют только Xray-трафиком. Туннель AmneziaWG пользователя всегда выходит на сервере, к которому он подключён. Маршрутизация AWG через другой хост потребовала бы site-to-site WG-туннеля плюс per-client policy-routing, чего этот проект пока не предоставляет.

### 7. Ограничивающие сети — сменить маскировочный домен REALITY

REALITY заимствует TLS-рукопожатие **маскировочного домена**, и клиент отправляет его как SNI. По умолчанию это `cloudflare.com`. Некоторые **ограничивающие сети блокируют TLS к определённым SNI** — клиент там видит, что TCP-соединение открывается, но рукопожатие **виснет (0 байт в ответ)**, тогда как обычный HTTPS работает. Решение — маскироваться под сайт, который эта сеть не блокирует.

Выберите домен, который **не заблокирован из сети клиента**, поддерживает **TLS 1.3 + HTTP/2** и не спрятан за нежелательным CDN — крупный «скучный» локально-популярный сайт идеален. Быстрая проверка со стороны клиента (`rc` 28 = блок/тихий дроп; `0` = чистый проход; `35`/`60` = TLS-ответ пришёл, не зависание — обычно проход, но перепроверьте: так же может выглядеть активное вмешательство):

```bash
curl -s -o /dev/null -w '%{exitcode}\n' --max-time 8 --resolve <sni>:443:<server-ip> https://<sni>/
```

Применение:

- **До первого деплоя** — отредактируйте `dest` и `serverNames` в `xray/conf/config.json.tmpl`, затем запустите `deploy.sh` (дефолт вообще не попадёт в эфир).
- **На работающем сервере** — в `xray/conf/config.json`, в `inbounds[0].streamSettings.realitySettings`, задайте `dest` = `"<sni>:443"` (хост **и** порт) и `serverNames` = `["<sni>"]` (только хост); затем `docker compose restart xray`. Существующих клиентов нужно **перевыпустить**: в каждом `clients/<name>_xray.vless` меняется только `sni=` (UUID/ключи те же) — перегенерируйте ссылку + QR, и SNI клиента должен совпадать с сервером.

> Целый IP сервера тоже может быть заблокирован на уровне TCP независимо от SNI. Если даже не-TLS порт (напр. 22) виснет из сети клиента, но работает откуда-то ещё — фильтруется сам IP, нужен другой адрес.

### 8. Отключить компонент (или включить обратно)

Хост может работать по одному протоколу. Достаточно повторного деплоя с флагом:

```bash
sudo ENABLE_AMNEZIAWG=0 ./deploy.sh    # убрать AmneziaWG (и DNS), оставить Xray REALITY
sudo ./deploy.sh                       # оба обратно (флаги по умолчанию = 1)
```

Повторный деплой удаляет контейнер отключённого сервиса, перестаёт собирать его
образ и — для AmneziaWG — снимает `amneziawg-module.service` и
`/etc/modules-load.d/amneziawg.conf`, чтобы модуль ядра больше не грузился и не
пересобирался при загрузке. Ключи, живые конфиги и клиентские файлы остаются на
месте, поэтому обратное включение возвращает тех же пиров/клиентов. Подробности
и допустимые значения: [Выбор компонентов](#выбор-компонентов).

Две оговорки:

- Существующие профили отключённого компонента **перестают работать** — в этом и
  смысл. Их файлы остаются в `clients/`, пока вы их не удалите (или не запустите
  `cleanup.sh`).
- Отключить последний оставшийся компонент нельзя; для сноса хоста есть
  `cleanup.sh`.

## Управление через AI-ассистента (Claude Code / Codex)

В репозитории есть **операторский skill `vpn`** — runbook, который позволяет Claude Code или Codex управлять всем флотом по запросам на обычном языке: выбрать нужный скрипт на нужном хосте и проверить результат. Превращает сценарии выше в однострочные просьбы.

**Настройка — ничего сверх `git clone`:**
- **Claude Code** авто-находит его как skill `vpn` в `.claude/skills/vpn/`.
- **Codex** авто-читает `AGENTS.md` (корень репо), который указывает на тот же runbook.
- *(Опционально)* показать его в нативном списке скиллов Codex:
  `ln -s "$(pwd)/.claude/skills/vpn" ~/.agents/skills/vpn`.

**Инвентарь хостов** (чтобы обращаться к серверам по алиасу, а не по IP): скопируйте шаблон и заполните — файл лежит вне репозитория, т.к. содержит IP/ключи:

```bash
mkdir -p ~/.config/vpn
cp .claude/skills/vpn/hosts.example.yml ~/.config/vpn/hosts.yml
$EDITOR ~/.config/vpn/hosts.yml        # алиас -> ip / os / роль / ssh-ключ
```

Писать руками не обязательно. Без инвентаря ассистент **создаст его** (спросит один-или-несколько серверов, адрес, пользователя и ключ *или* пароль) либо **импортирует существующий/старый файл**, если дать путь — и не выполнит ни одной операции, пока инвентаря нет. Можно в любой момент просто сказать *«добавь хост …»*. Хост принимает **IP или FQDN** и аутентифицируется **SSH-ключом (рекомендуется) или паролем** (`sshpass`; ассистент предупредит и предложит `ssh-copy-id`).

**Примеры** (просто пишете ассистенту):

| Вы говорите | Что делает |
|-------------|------------|
| «добавь хост `de`, `de.example.com`, user root, ключ `~/.ssh/id_ed25519`» | добавляет хост в `~/.config/vpn/hosts.yml` (создаёт, если нет), предлагает проверку связи |
| «разверни VPN на `de`» | rsync/clone репо → проверка swap → `docker-install.sh` → `deploy.sh` → проверяет контейнеры/модуль, печатает порты для открытия |
| «разверни `de`, только Xray» | то же, но с `ENABLE_AMNEZIAWG=0` — без kernel-модуля и без AWG-контейнера |
| «статус `de`» | контейнеры, модуль, версии образов, число AWG-пиров / Xray-клиентов, egress-IP |
| «добавь логин `alice` на `us`» | `add-client.sh alice`, отдаёт `.conf` / VLESS-ссылку / QR |
| «нужен логин, подключение к `us`, выход в `de`» | уточняет entry/exit, настраивает **Xray**-chaining (`us` → `de`) и отдаёт Xray-профиль (cross-server landing только Xray) |
| «выпусти `alice` через `de`» | `xray/add-upstream.sh` + `xray/set-route.sh alice de` |
| «верни `alice` на локальный выход» | `xray/set-route.sh alice direct` |
| «удали `alice` на `us`» | `remove-client.sh alice` |
| «пересобери kernel-модуль на `us`» | останавливает `amneziawg`, запускает `rebuild-amneziawg.sh`, поднимает обратно |
| «снеси `us`» | подтверждает, затем `cleanup.sh` |

Закрепить версию компонента можно прямо в просьбе (например, «разверни `de` с Xray v26.6.1») — ассистент передаст `XRAY_RELEASE=…` в `deploy.sh`. Вы остаётесь в петле: ассистент подтверждает деструктивные/внешние действия перед запуском.

## Как это работает

### AmneziaWG

AmneziaWG — обфусцированный форк WireGuard, добавляющий мусорные пакеты и манипуляции заголовками для сопротивления DPI-блокировкам. При развёртывании сервер генерирует случайные параметры обфускации (Jc, Jmin, Jmax, S1–S4, H1–H4), которые запекаются и в серверный, и в клиентский конфиги, делая отпечаток трафика каждого развёртывания уникальным.

Добавление или удаление клиента применяется на лету через `awg syncconf` — без рестарта контейнера — поэтому существующие сессии не страдают. Каждый клиент получает выделенный IP в подсети 10.8.0.0/24 с pre-shared key для постквантовой forward secrecy. Сам kernel-модуль собирается на хосте (а не в контейнере) и перезагружается только при обновлении ядра (см. сценарий 3).

### Xray REALITY

Xray REALITY делает VPN-трафик похожим на обычный HTTPS к **маскировочному домену** (по умолчанию `cloudflare.com`). В отличие от традиционных TLS-прокси, REALITY не требует домена или сертификата — он заимствует TLS-рукопожатие этого сервера-назначения, что сильно затрудняет его обнаружение системами цензуры. В **ограничивающих сетях, где дефолтный маскировочный SNI заблокирован**, смените его на сайт, который эта сеть не блокирует — см. [сценарий 7](#7-ограничивающие-сети--сменить-маскировочный-домен-reality).

Управление клиентами требует рестарта контейнера (обычно менее 2 секунд). Каждый клиент идентифицируется по UUID и подключается по протоколу VLESS с flow control `xtls-rprx-vision`.

### DNS

Все DNS-запросы VPN-клиентов перехватываются через iptables DNAT и перенаправляются на внутренний экземпляр dnscrypt-proxy. Этот резолвер шифрует запросы через DNSCrypt или DNS-over-HTTPS к Cloudflare и Google, требует валидацию DNSSEC и no-logging от upstream-резолверов. Контейнер DNS не открыт на хост — он доступен только внутри Docker-сети.

## Заметки по безопасности

- **Сборка из исходников, версия закрепляется на каждой сборке** — kernel-модуль AmneziaWG, awg-tools, Xray-core и dnscrypt-proxy компилируются из исходников. Каждое развёртывание определяет релиз (latest или закреплённый `*_RELEASE` — см. [Версии компонентов](#версии-компонентов)), закрепляет его до иммутабельного commit-**SHA** и фетчит по этому SHA — так сдвинутый тег не может незаметно изменить сборку; версия фиксируется тегом образа. Geo-базы Xray берутся последними и намеренно не закрепляются. Никаких готовых бинарников.
- **Минимальные привилегии контейнера** — контейнер AmneziaWG имеет только `CAP_NET_ADMIN`; у него нет `CAP_SYS_MODULE` и нет маунта `/lib/modules`, поэтому компрометация контейнера не позволяет загрузить код в ядро хоста. Модуль грузится на хосте и сохраняется через `/etc/modules-load.d/`.
- **Сетевая изоляция VPN-клиентов** — правила forward-пути в `awg0.tmpl` дропают трафик клиент↔клиент, эндпоинт облачной метадаты (`169.254.169.254`, `168.63.129.16`), диапазоны RFC1918 и CGNAT. `deploy.sh` также ставит хостовое правило `INPUT` (сохраняется как `vpn-host-firewall.service`), блокирующее новые соединения из docker-подсети к хосту, — закрывая путь к хост-сервисам (например, sshd), которых не видит облачный фаервол.
- **Приватность DNS** — *весь* трафик клиентов на порт 53 (любое назначение) принудительно DNAT'ится на внутренний резолвер dnscrypt-proxy; клиенты не могут обойти его внешним plain-DNS сервером. (DoH/DoT на 443/853 на этом уровне перехватить нельзя.)
- **Маршрутизация Xray** блокирует соединения с приватными диапазонами IP (`geoip:private`) для предотвращения SSRF.
- **Изоляция ключей** — все ключи генерируются на сервере и никогда не передаются. Скрипты, пишущие секреты, работают под `umask 077`; файлы ключей, живые конфиги и каталог `clients/` имеют права `chmod 600`/`700`.
- **Фаервол и хардненинг SSH в остальном не автоматизированы** — помимо хостового правила INPUT выше, настройте облачный фаервол и fail2ban отдельно, а перед продакшном закройте SSH до ключей. Некоторые VPS/cloud-образы включают парольную аутентификацию (через `/etc/ssh/sshd_config.d/*cloud*`) и идут с логин-пользователем, у которого есть пароль + беспарольный sudo — путь к root через брутфорс. Убедившись, что вход по ключу работает, добавьте drop-in **с именем, сортирующимся первым** (sshd берёт *первое* встреченное значение, поэтому файл `99-` перебивается `60-cloudimg-settings.conf` — используйте `00-`):
  ```bash
  printf '%s\n' 'PasswordAuthentication no' 'KbdInteractiveAuthentication no' \
    'X11Forwarding no' 'PermitRootLogin prohibit-password' \
    | sudo tee /etc/ssh/sshd_config.d/00-hardening.conf
  sudo sshd -t && sudo systemctl reload ssh   # reload (не restart) сохраняет текущую сессию
  sudo passwd -l <login-user>                  # заблокировать пароль аккаунта; вход по ключу не затрагивается
  ```
  Проверьте **свежим** подключением по ключу перед отключением (уберите строку `PermitRootLogin`, если логин-пользователь не root).
- Сгенерированные ключи, конфиги клиентов и `docker-compose.yml` находятся в gitignore и никогда не коммитятся.

## Устранение неполадок

**Контейнер не запускается:**
```bash
docker compose logs <service>     # Проверить логи на ошибки
docker compose ps                 # Проверить статус и health контейнеров
```

**Контейнер AmneziaWG перезапускается / не держится:**
```bash
lsmod | grep amneziawg                   # Модуль должен быть загружен на ХОСТЕ
docker exec vpn-amneziawg awg show           # Статус интерфейса (если контейнер поднят)
```
Если модуля нет, выполните сценарий 3 (`rebuild-amneziawg.sh`). У контейнера по дизайну нет `CAP_SYS_MODULE`, и он не может загрузить модуль сам.

**Клиент не может подключиться (AWG):**
```bash
docker exec vpn-amneziawg awg show awg0      # Проверить, есть ли пир в списке
```

**Клиент не может подключиться (Xray):**
- Убедитесь, что порт 443/tcp открыт в облачном фаерволе
- Проверьте, что VLESS-ссылка соответствует публичному ключу и Short ID сервера

**DNS не резолвится:**
```bash
docker exec vpn-dns drill @127.0.0.1 example.com   # Проверить внутренний DNS
```

**Пересоздать всё с нуля:**
```bash
./cleanup.sh && sudo ./deploy.sh
```

**Обновление ядра — модуль AmneziaWG больше не грузится:**

После обновления ядра Ubuntu `.ko` AmneziaWG, собранный под предыдущее ядро, не загрузится. Остановите контейнер, пересоберите модуль под новое ядро, перезапустите:

```bash
docker compose stop amneziawg
sudo ./rebuild-amneziawg.sh
docker compose start amneziawg
```

`rebuild-amneziawg.sh` собирает модуль в одноразовом Ubuntu-контейнере под вашу версию ядра, проверяет полученный `.ko` (`modinfo`), атомарно заменяет установленный модуль и автоматически откатывается на бэкап, если `modprobe` не удаётся. Бэкапы хранятся в `/var/backups/amneziawg-kmod/<kver>/` (3 последних).

## Полный сброс

Чтобы полностью вернуть сервер в чистое состояние:

```bash
./cleanup.sh
```

Запрашивает подтверждение, затем:
- Останавливает и удаляет все контейнеры и Docker-сеть
- Удаляет Docker-образы (`amneziawg`, `xray`, `dns`)
- Удаляет все сгенерированные ключи, серверные конфиги, конфиги клиентов и QR-коды
- Удаляет хост-артефакты, установленные `deploy.sh`: правило `INPUT`, `vpn-host-firewall.service` и `/etc/modules-load.d/amneziawg.conf` (kernel-модуль остаётся загруженным до следующей перезагрузки)

После очистки `sudo ./deploy.sh` поднимает всё заново с нуля.
